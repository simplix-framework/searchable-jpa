# Documentation guide

## Structure

English and Korean pages are kept under `docs/en/` and `docs/ko/` with the same file names, and a page has the same headings, listings, figures and table shapes in both languages. Docsify is configured in `docs/index.html`, and `docs/assets/` holds the shared version selector code. The order of the sidebar is the reading order. Each page relies only on the pages before it and its last section leads to the next page.

A guide page is written in this order.

1. What the page gives and what it relies on
2. A figure
3. The smallest example and its variations
4. A table of rules
5. Refused requests
6. Related settings
7. The next step

Add a new page to the directory and the sidebar of both languages. Link a neighbouring page as `./basic-usage.md` and a figure as `./_images/name.svg`. Changelog entries of past versions record the behavior of their time, so do not rewrite them to the current behavior.

## Listings

Java, HTTP and JSON listings are not written into a page; they come from files the test suite compiles and runs.

| Listing | Location |
| --- | --- |
| Java | `spring-boot-starter-searchable-jpa/src/test/java/dev/simplecore/searchable/docs` |
| Requests | `spring-boot-starter-searchable-jpa/src/test/resources/docs-examples/requests`, `rejected` |
| Responses | `spring-boot-starter-searchable-jpa/src/test/resources/docs-examples/responses` |

A page names the source above the listing and leaves the block empty.

````markdown
<!-- snippet: PostService.java#service -->
```java
```
````

The part after `#` is a region name; without it the whole file is taken. A source marks a region with comments, and regions of the same name are joined in order.

```text
// docs:start service
...
// docs:end service
```

```bash
node scripts/doc-snippets.mjs
./gradlew :spring-boot-starter-searchable-jpa:test --tests '*DocumentationExamplesTest'
```

The first command fills the marked blocks from their sources. The `DocumentationExamplesTest` of the second command asserts that every request under `requests` succeeds, that every request under `rejected` is refused with 400, and that the results a page states are the results returned. When you add a request example, state its expected result in that test.

## Figures

Figures are generated by the modules in `scripts/figures/`; an SVG is never edited by hand. The settings are in `scripts/figures/document-figures.json`, whose paths are relative to that folder, and the drawing library and the checks are `scripts/docfigures` of the svg-diagrams skill. `<skill>` below is the directory of that skill.

```bash
python3 <skill>/scripts/docfigures/build.py --config scripts/figures/document-figures.json
python3 scripts/verify-figures.py <skill>/scripts/docfigures --render build/figures
```

One function draws a figure in both languages from its texts. A figure shows one relation that sentences carry badly, and each function of a module states that claim in a comment.

## Feature ledger

`scripts/docs-ledger.json` lists what the documentation has to cover and the page that explains it. Names such as operators, annotation attributes, service methods, setting keys and message keys are read from the sources, so adding a name to the sources fails the check until a page has it. A behavior without a name is registered under `features` with the page that explains it and the code tokens that page has to show.

A feature counts as covered when a guide page shows it as code and a reference page lists it, in both languages.

## Local preview and checks

```bash
./scripts/build-docs.sh
python3 -m http.server 3000 --directory build-docs
```

Open `http://localhost:3000/#/en/` or `http://localhost:3000/#/ko/`. Use an HTTP server rather than `file://`. The build copies the pages of both languages and the shared files, writes the version of `build.gradle` or `DOCS_VERSION` into the cover page and converts links to the Docsify form. `build-docs/` is output that can be generated again.

```bash
npm ci
npm run test:docs
npm run test:docs:e2e
```

| Check | What it asserts |
| --- | --- |
| Listings | Marked listings equal their sources, and Java, HTTP and JSON listings name a source |
| Coverage | Every entry of the feature ledger is on the pages of both languages |
| Parity | Both languages have the same pages, headings, listings, figures, tables and sidebar, and links resolve |
| Version navigation | The path arithmetic of the version selector and the preparation of a deployment |

The documentation checks need Node.js 22 or later. The e2e check starts a test server on port 8764, so keep that port free.
## Versioned deployment

The `Deploy Documentation` GitHub Actions workflow publishes `gh-pages`. A documentation change on `master` refreshes the `snapshot/` folder. Manual dispatch with a stable version such as `2.0.0` checks out `v2.0.0` and builds its content. The workflow obtains current navigation tooling separately so archived text can retain its original content while sharing repaired navigation.

`scripts/prepare-docs.mjs` combines the previous site with the new build. It replaces the selected version directory, preserves other releases and the snapshot, updates shared navigation assets in archived HTML and generates `versions.json`. Releases use numeric descending order. Publishing a release does not delete the development docs.

The root page redirects to the highest available stable release, or the snapshot when there is no stable release. Query and hash state are retained. The selector operates on sibling version directories, preserves the requested language/page/heading and checks page availability before navigation. A missing page falls back to the language home page, then English. A failed network request leaves the current page open.

Published site: [Searchable JPA documentation](https://simplix-framework.github.io/searchable-jpa/). GitHub Pages must serve the `gh-pages` branch root. Repository workflow permissions must allow the deployment workflow to write that branch.

## Troubleshooting

- A local unversioned preview intentionally omits the version selector. Test it through `npm run test:docs:e2e` or the fixture server (`node scripts/docs-test-server.mjs`).
- If the version list fails, use the visible retry button and inspect the parent `versions.json` response. Check project subpaths as well as domain-root paths.
- If content or search appears stale, verify the selected version and language, reload the page and inspect CDN/plugin requests. Docsify 5 plugins use `dist/plugins/` paths.
- If a figure is absent, check filename case and whether the SVG exists in the `en` and `ko` directories. Build output is regenerated, so edit `docs/`, not `build-docs/`.
- If a manual release deployment fails, verify that its exact `vX.Y.Z` tag exists and that the version input contains only three numeric components.
